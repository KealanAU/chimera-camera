# V1: Chimera Camera Surface Layer

This document defines the first implementation target for `chimera-camera`.

V1 is not a full VisionCamera port. V1 is the smallest useful Lynx-native camera
surface that proves JavaScript can interact with native camera engines on iOS
and Android through Lynx.

## Goal

Build a plain JavaScript/TypeScript API over platform-native camera engines:

- JavaScript/TypeScript is the public developer surface.
- Android camera work is handled by Kotlin and CameraX.
- iOS camera work is handled by Swift/Objective-C++ and AVFoundation.
- Lynx provides the bridge for native views, imperative methods, and events.

This recreates the useful role Nitro plays in VisionCamera, but only as a thin
Lynx-native surface layer. We are not rebuilding Nitro, JSI, codegen, React
components, React hooks, or frame processors in V1.

V1 also ships a mock adapter for Lynx Explorer, web preview, and app-level tests.
The mock is not a hardware simulator. It is a plain JS implementation of the
same public contract so apps can prove UI, upload, and error flows before native
iOS/Android registration is complete.

## Surface Model

V1 has two bridge surfaces:

1. `CameraView`
   - A Lynx native UI component.
   - Owns preview rendering.
   - Receives view props.
   - Exposes imperative methods.
   - Emits view-scoped events.

2. `CameraModule`
   - A native module accessed from JavaScript.
   - Handles non-view operations such as permissions and device discovery.
   - Does not render preview.

Keeping these separate matters. Permissions and devices are app/module concerns;
preview, focus, zoom, capture, and recording are view/session concerns.

## Public JavaScript API

The public API should be plain TypeScript and framework-neutral. React, Vue,
Svelte, or any Lynx JS integration should be able to use the same underlying
surface.

The authoritative type definitions live in [`src/types.ts`](src/types.ts).
This document describes the behavioral contract; where the two disagree,
`src/types.ts` wins. The public surface includes:

- Status and mode unions: `PermissionStatus`, `CameraPosition`,
  `TargetCameraPosition`, `TorchMode`, `FlashMode`, `PreviewResizeMode`.
- Data shapes: `Size`, `Point`, `CameraDevice`, `CameraPermissions`,
  `PhotoFile`, `VideoFile`, `CapturePhotoOptions`, `StartRecordingOptions`.
- Contracts: `CameraModule`, `CameraViewProps`, `CameraViewMethods`,
  `CameraAdapter`, and the event payload types.

The interface sketches later in this document are illustrative; keep them in
sync with `src/types.ts` or trim them when they drift.

## CameraModule V1

`CameraModule` should expose:

```ts
export interface CameraModule {
  getPermissions(): Promise<CameraPermissions>
  requestCameraPermission(): Promise<PermissionStatus>
  requestMicrophonePermission(): Promise<PermissionStatus>
  getAvailableCameraDevices(): Promise<CameraDevice[]>
  getDefaultCamera(position: TargetCameraPosition): Promise<CameraDevice | null>
}
```

Native expectations:

- Android uses app/activity permission APIs, not React Native permission helpers.
- iOS uses `AVCaptureDevice.authorizationStatus(for:)` and
  `AVCaptureDevice.requestAccess(for:)`.
- Microphone permission is only required for video recording with audio.
- Permission errors should normalize into stable JS error codes.

## CameraView V1

`CameraView` should be registered as a native Lynx element, likely using the tag
name:

```text
camera-view
```

Suggested props:

```ts
export interface CameraViewProps {
  active?: boolean
  cameraId?: string
  facing?: TargetCameraPosition
  resizeMode?: PreviewResizeMode
  torch?: TorchMode
  zoom?: number
  enableAudio?: boolean
  onReady?: (event: CameraReadyEvent) => void
  onError?: (event: CameraErrorEvent) => void
  onRecordingStarted?: (event: RecordingStartedEvent) => void
  onRecordingFinished?: (event: RecordingFinishedEvent) => void
}
```

Imperative methods:

```ts
export interface CameraViewMethods {
  ping(): Promise<{ ok: true }>
  capturePhoto(options?: CapturePhotoOptions): Promise<PhotoFile>
  startRecording(options?: StartRecordingOptions): Promise<void>
  stopRecording(): Promise<VideoFile>
  focusAtPoint(point: Point): Promise<void>
  setZoom(value: number): Promise<void>
  setTorch(mode: TorchMode): Promise<void>
}
```

`ping()` is intentionally part of the bridge spike. It proves JS can call a
native view method before camera behavior exists.

## Events

Use a stable event detail shape across platforms:

```ts
export interface CameraReadyEvent {
  deviceId: string
}

export interface CameraErrorEvent {
  code: string
  message: string
  cause?: unknown
}

export interface RecordingStartedEvent {
  path?: string
}

export interface RecordingFinishedEvent {
  file: VideoFile
}
```

Event naming should be consistent across Android and iOS. Native platform event
mechanisms can differ, but JavaScript should receive the same event names and
`detail` shapes.

## Native Bridge Targets

Android:

- Register `camera-view` through Lynx `Behavior` / `LynxUI`.
- Expose methods with `@LynxUIMethod`.
- Emit events with `LynxDetailEvent`.
- Wrap `androidx.camera.view.PreviewView` when preview starts.

iOS:

- Register `camera-view` through Lynx `LynxUI` registration.
- Expose methods through `LYNX_UI_METHOD`.
- Emit detail/custom events through the Lynx iOS event pipeline.
- Render preview with `AVCaptureVideoPreviewLayer`.

## Bridge Spike Acceptance Criteria

The first implementation pass is complete when the example app can:

- Render a visible native `camera-view` placeholder.
- Pass props from JS into native code.
- Call `ping()` on the native view and receive `{ ok: true }`.
- Receive a native `ready` event in JavaScript.
- Build the TypeScript API without React Native imports.
- Contain no React components, hooks, Nitro specs, JSI bindings, or
  `react-native-*` runtime dependencies.
- Use `@vyui/camera/mock` to exercise capture flows when native camera
  code is absent.

Camera preview is not required for this spike.

## Mock Adapter

The package exports a mock adapter from:

```ts
import { createMockCameraModule } from '@vyui/camera/mock'
```

The mock should:

- return authorized permissions by default
- expose fake front and back camera devices
- return a small JPEG fixture from `capturePhoto()`
- return deterministic metadata from `startRecording()` / `stopRecording()`
- allow apps to pass custom permissions, devices, photo fixtures, and delays

Production apps should prefer the real native module and only fall back to the
mock intentionally.

## Interim: Module-Level System Camera Capture

Ahead of the bridge spike, the iOS module already ships `capturePhoto()` on
`CameraModule`, presenting the system camera UI (`UIImagePickerController`)
and returning a base64 JPEG with a `memory://` pseudo-path. See
[ROADMAP.md](../../ROADMAP.md) milestone M1.

This is a deliberate stepping stone, not part of the V1 contract:

- V1 places capture on the `camera-view` session, not the module.
- V1 requires a real local file path. Base64 across the bridge costs 3–8 MB
  per 12 MP photo and should be replaced by writing a temp file natively and
  returning its path.

The interim capture is exposed through the same `CameraAdapter` surface, so
app code should not need changes when view-level capture replaces it.

## Camera MVP Acceptance Criteria

After the bridge spike, V1 camera behavior is complete when real devices can:

- Request/check camera permission.
- Request/check microphone permission.
- List available camera devices.
- Render live preview.
- Switch/select front and back cameras.
- Capture a photo and return a local file path.
- Start and stop video recording and return a local file path.
- Set zoom where supported.
- Set torch where supported.
- Focus at a point where supported.
- Survive mount/unmount and app background/foreground without crashing.

## Explicit Non-Goals

V1 does not include:

- React Native compatibility.
- React components or hooks.
- Web support.
- Nitro Modules.
- JSI.
- Frame processors.
- Skia integration.
- Barcode scanning.
- Depth data.
- RAW capture.
- HDR tuning beyond what is required by default platform behavior.
- Codegen.

## Upstream Reference Strategy

Use VisionCamera as a reference and selective port source, not as a runtime
dependency.

High-value upstream files to study first:

- iOS:
  - `HybridCameraSession.swift`
  - `HybridPreviewView.swift`
  - `HybridCameraPhotoOutput.swift`
  - `CapturePhotoDelegate.swift`
  - `HybridCameraVideoOutput.swift`
- Android:
  - `HybridCameraSession.kt`
  - `ConstraintResolver.kt`
  - `HybridPreviewView.kt`
  - `HybridPhotoOutput.kt`
  - `HybridVideoOutput.kt`
  - `HybridVideoRecorder.kt`

When porting, replace Nitro/RN types with local Lynx-native types and preserve
MIT license attribution for copied or substantially derived source.
