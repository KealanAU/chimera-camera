The bridge spike is the first executable milestone. It should prove that JavaScript can mount a native Lynx camera element, pass props, call a native view method, and receive a native event.

It does not need to start a camera session.

## Acceptance criteria

The spike is complete when the example app can:

- Render a visible native `camera-view` placeholder.
- Pass props from JavaScript into native code.
- Call `ping()` on the native view and receive `{ ok: true }`.
- Receive a native `ready` event in JavaScript.
- Keep the TypeScript API free of UI-framework runtime imports.

## Public shape

The bridge should expose the same public names that the later camera implementation will use:

```ts
export interface CameraViewMethods {
  ping(): Promise<{ ok: true }>
}
```

`ping()` is intentionally a throwaway capability. It verifies the imperative method path while avoiding camera behavior in the first pass.

## Native placeholder

The placeholder should be visibly native on each platform. It can be a simple colored view with a label or a minimal platform-native layout. The important part is proving that the Lynx element registration resolves and renders.

The target tag name is:

```text
camera-view
```

## Ready event

The placeholder should emit the same event channel that the real preview will use later:

```ts
export interface CameraReadyEvent {
  deviceId: string
}
```

For the spike, `deviceId` can be a deterministic placeholder such as `bridge-placeholder`. The event shape should not change when real devices are added.

## What comes next

After the spike, native work can proceed behind the same surfaces:

1. Add `CameraModule` permission and device discovery methods.
2. Attach real preview rendering to `CameraView`.
3. Implement capture, recording, zoom, torch, focus, and lifecycle handling.
